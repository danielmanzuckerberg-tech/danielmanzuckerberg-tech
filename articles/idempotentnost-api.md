# Один запрос. Один результат.

> Бортовой журнал Moritz · API Design · 5 минут

Клиент отправил запрос, сервер его выполнил, а ответ потерялся в сети. Для клиента это ошибка. Для сервера — уже совершённое действие. Повторная попытка не должна превращаться во вторую оплату, второе письмо или второй заказ.

Идемпотентность — договор о том, что повтор одной операции не создаёт дополнительного побочного эффекта. Это не гарантия того, что сеть доставит запрос только один раз.

## Ключ обозначает намерение

Клиент создаёт случайный ключ на одну логическую операцию и использует его при повторах. Нельзя генерировать новый ключ после каждого тайм-аута: для сервера это уже другое намерение.

Область уникальности должна включать пользователя или организацию и тип операции. Сам по себе заголовок `Idempotency-Key` не подтверждает личность и не даёт доступа к чужому результату.

## Сначала зарезервировать, потом выполнить

Наивная последовательность «проверить наличие → выполнить → сохранить» ломается при двух одновременных запросах. Оба успеют увидеть отсутствие записи.

Нужна атомарная резервация: уникальное ограничение на владельца, операцию и ключ; затем транзакция или явно описанная машина состояний. Полезные состояния — `processing`, `succeeded` и `failed`, с определёнными правилами восстановления.

Вместе с ключом храните хэш нормализованного тела запроса. Повтор с тем же ключом, но другим содержимым должен завершаться конфликтом, а не неожиданно возвращать результат чужой операции.

## Побочный эффект за пределами базы

Транзакция вашей базы не охватывает SMS-провайдера или платёжный шлюз. Сценарий «провайдер выполнил действие, процесс упал до сохранения результата» всё ещё возможен.

Если провайдер поддерживает идемпотентность, передавайте ему стабильный ключ. Если нет — проектируйте outbox, обработку неопределённого результата и процедуру сверки. Нельзя обещать exactly-once только потому, что в таблице есть уникальный индекс.

## Что возвращать при повторе

- Для завершённой операции — сохранённые статус и тело ответа, доступные только тому же владельцу.
- Для ещё выполняющейся — документированный ответ о состоянии обработки; не запускайте её заново.
- Для несовпадающего тела — конфликт с понятным объяснением.
- Для истёкшего срока хранения — поведение, явно описанное в контракте API.

Срок хранения должен покрывать реальный период повторов клиентов. Для долгоживущих бизнес-операций одной очистки ключей по TTL недостаточно: бизнес-идентификатор тоже должен защищать от дубликатов.

## Проверка перед выпуском

Отправьте два одинаковых запроса одновременно. Оборвите соединение после выполнения действия. Повторите запрос с другим телом и тем же ключом. Попробуйте использовать ключ другого пользователя. Перезапустите обработчик между внешним вызовом и фиксацией результата.

Если система не может объяснить результат каждого эксперимента, надёжность пока остаётся предположением.
