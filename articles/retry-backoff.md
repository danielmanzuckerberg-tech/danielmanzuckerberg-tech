# Повторять — не значит ломиться.

> Бортовой журнал Moritz · Reliability · 4 минуты

Сервис замедлился, клиенты начали повторять запросы, нагрузка выросла ещё сильнее. Так механизм восстановления сам превращается в причину аварии. Хорошая политика повторов — прежде всего политика ограничений.

## Не любую ошибку стоит повторять

Ошибка валидации не станет успешным запросом после паузы. Неверные права доступа тоже. Обычно повторяют временные сетевые сбои, отдельные ответы сервера и ограничение частоты — только если контракт операции это допускает.

Тайм-аут не означает, что сервер ничего не сделал. Для операций с побочными эффектами сначала нужна [идемпотентность](./idempotentnost-api.md).

## Пауза должна расти, но не бесконечно

Экспоненциальный backoff увеличивает задержку после каждой неудачи. Верхняя граница не даёт паузе вырасти до бессмысленного значения. Jitter добавляет случайность: тысячи клиентов не должны просыпаться одновременно.

Пример расчёта полной случайной задержки на TypeScript:

```ts
function fullJitter(attempt: number, baseMs = 500, capMs = 30_000) {
  const ceiling = Math.min(capMs, baseMs * 2 ** attempt)
  return Math.floor(Math.random() * ceiling)
}
```

Здесь `Math.random()` подходит: задержка не является секретом. Для кодов входа и токенов этот источник случайности использовать нельзя.

## Общий бюджет важнее количества попыток

Ограничьте число попыток, общую продолжительность операции и время одного запроса. Отмена со стороны пользователя должна прекращать и текущий запрос, и ожидание следующего.

Если каждая из нескольких вложенных систем повторяет запрос самостоятельно, итоговое число обращений может быстро вырасти. Выберите уровень, который отвечает за повторы, и согласуйте его с нижележащими библиотеками.

## Уважайте Retry-After

Сервер может вернуть задержку в секундах или HTTP-дату. Учитывайте оба варианта. Не уменьшайте эту задержку своим jitter. Если ожидание выходит за бюджет пользовательской операции, верните понятное состояние или перенесите работу в фоновую очередь.

## Когда лучше остановиться

Circuit breaker не лечит зависимость. Он временно прекращает бесполезные обращения и даёт ей восстановиться. После паузы пропустите ограниченное количество пробных запросов, а не весь накопившийся поток.

Для фоновой задачи после исчерпания повторов нужен отдельный путь: карантин, ручная проверка или dead-letter queue. Бесконечный повтор скрывает проблему вместо её решения.

## Минимальный набор наблюдений

Записывайте номер попытки, причину повтора, запланированную задержку и общий возраст задачи. Не записывайте секреты или полное содержимое пользовательских сообщений. Сравнивайте успешность после повторов с долей исходных ошибок: высокая частота «спасённых» запросов может маскировать деградацию.
